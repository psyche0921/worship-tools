# 인수인계: v1(정적 페이지) → v2(자체 서버 + DB)

claude.ai 대화에서 v1을 만들어 GitHub Pages로 배포했습니다. 이 문서는 그 맥락을 코드 작업으로 넘기기 위한 정리입니다.

> **2026-10-19 업데이트**: 4장의 질문은 대부분 정해졌습니다. 확정된 v2 설계(170번 서버, `bbc.ppsoft.kr`, 관리자/팀원 역할)는 [`docs/v2-design.md`](v2-design.md)를 보세요.

## 1. 사용자 업무 흐름

- **매주 (주말 전)**: 카톡 단톡방으로 세트리스트 메시지를 받습니다. 사용자가 복사해서 페이지에 붙여넣고, 재생목록을 만들어 단톡방에 링크를 공유합니다. 메시지를 자동으로 수집하는 기능은 원하지 않습니다(직접 붙여넣는 방식으로 충분).
- **매주 월요일**: 일요일 예배 라이브 영상(유튜브)을 바탕으로 설교 구간 쇼츠 몇 편을 기획합니다. 예전에는 Gemini Gem을 썼는데, Gem이 skill로 바뀌면서 지침을 `SKILL.md` 파일로 가지고 있습니다. **이 파일은 저장소에 아직 없습니다. 사용자에게 받아야 합니다.**
- 사용자는 안드로이드 폰 브라우저에서 주로 씁니다. 그래서 모바일 우선 UI와 공유창(Web Share API) 연동이 중요합니다.

## 2. 현재 v1 구현 요약 (`index.html`)

| 영역 | 구현 |
|---|---|
| 세트리스트 파싱 | `parseMessage()`: 구분선으로 블록 분리, 6자리 날짜 추출, `youtu.be` / `watch?v=` / `live/` / `shorts/` ID 추출(`?si=` 제거) |
| 재생목록 생성 | Google Identity Services 토큰 클라이언트(브라우저 OAuth, scope `youtube`)로 YouTube Data API v3 호출. `playlists.insert` 다음 `playlistItems.insert`를 곡마다 실행하고, 409/5xx는 재시도 |
| 쇼츠 기획 | 브라우저에서 Gemini `generateContent`를 직접 호출. `system_instruction`에 SKILL.md(frontmatter 제거), 영상은 `file_data.file_uri` + `video_metadata` 오프셋, `mediaResolution: LOW`. 기본 모델 `gemini-3.8-flash`(설정에서 변경 가능) |
| 설교 구간 자동 찾기 | 같은 영상을 JSON 응답 모드로 요청해 `{start, end, title}`을 받음 |
| 결과 표시 | 마크다운을 블록/인라인 조각(run)으로 파싱(`parseBlocks`, `parseInline`)하고, 같은 구조로 HTML(`blocksHtml`)과 PDF(`buildPdf`)를 그림. `##` 제목 기준으로 쇼츠별 카드 분리 |
| PDF | jsPDF + 나눔고딕(Identity-H로 필요한 글자만 넣음). 링크 주석, 표, 목록, 쪽 번호를 직접 배치. 공유는 `navigator.share({files})`, 지원하지 않으면 다운로드 |
| 작업 기록 | `localStorage`에 저장. 세트리스트는 최대 100개, 쇼츠는 최대 60개. 다시 열기와 2단계 삭제 확인 지원 |

### localStorage 키 (v2로 옮길 데이터)

| 키 | 내용 |
|---|---|
| `clientId` | OAuth 클라이언트 ID |
| `geminiKey`, `gModel` | Gemini API 키, 모델명 |
| `skillPath`, `skillText` | SKILL.md 경로 또는 직접 붙여넣은 내용 |
| `hist.setlist` | `[{key: playlistId, title, url, at, ok, total, songs: [{id, name, notes[]}]}]` |
| `hist.shorts` | `[{key: 's'+at, id: videoId, start, end, text: 원문 마크다운, at, title, extra}]` |
| `shortsLast` | 예전 형식(1건). `hist.shorts`로 옮기는 코드가 있음 |
| `tab` | 마지막으로 연 탭 |

## 3. v2 목표 (사용자 요청)

> "서버가 있는데 서버에 배포하고 데이터는 DB로 관리하고 싶어"

- 사용자 소유 서버에 배포
- 작업 기록(세트리스트, 쇼츠)을 DB에 저장해서 기기 간에 공유(폰/PC)
- 기존 기능은 모두 유지: 파싱, 재생목록 생성, 쇼츠 기획, PDF 공유, `#t=` 표기 제거, 기록 보기와 삭제

## 4. 먼저 사용자에게 확인할 것

1. **서버 환경**: OS, 이미 쓰는 스택(Docker, nginx, Node, Python 등), 도메인과 HTTPS 여부. Google OAuth의 승인된 JavaScript 원본은 HTTPS여야 하고 새 도메인을 등록해야 합니다.
2. **DB 선택**: 혼자 또는 소수가 쓰는 규모라 SQLite로 충분할 수 있습니다. 이미 운영 중인 DB가 있으면 그걸 씁니다.
3. **사용자 범위**: 본인만 쓰는지, 예배팀원도 같이 쓰는지. 이에 따라 사이트 로그인과 권한 설계가 달라집니다.
4. **SKILL.md**: 저장소에 넣을지(공개 저장소라 누구나 볼 수 있음), 서버 설정이나 DB에 둘지, 화면에서 수정할 수 있게 할지.
5. 저장소를 계속 **공개**로 둘지.

## 5. 설계 시 고려할 점 (제안이며 아직 확정 아님)

- **API 키를 서버로 옮기기**: Gemini 키를 서버 환경변수로 옮기면 브라우저에 키가 남지 않습니다. 대신 **사이트 자체에 접근 제어가 반드시 있어야** 합니다. 없으면 누구나 내 키로 Gemini를 호출할 수 있습니다.
- **YouTube OAuth**: 지금처럼 브라우저에서 토큰을 받는 방식을 유지하면 서버는 기록만 저장하면 되므로 가장 간단합니다. 서버가 리프레시 토큰을 저장해 대신 호출하게 바꾸려면, OAuth 앱이 '테스트' 상태일 때 리프레시 토큰이 7일 뒤 만료된다는 점을 고려해야 합니다(게시 상태와 검수 요건은 현재 Google 문서로 확인 필요).
- **쇼츠 생성 시간**: 1~2분 걸릴 수 있습니다. 서버에서 호출한다면 프록시 타임아웃이나 작업 큐/폴링 방식을 고려해야 합니다.
- **PDF**: 지금은 브라우저에서 만들고 공유창으로 보냅니다. 이 방식이 안드로이드 공유창과 잘 맞으므로 서버로 옮길 필요는 낮습니다.
- **기존 기록 이전**: 사용자 브라우저의 `hist.*`를 서버로 올리는 가져오기 기능(1회성)이 있으면 좋습니다.
- **세트리스트 원문 저장**: v1은 파싱 결과만 저장합니다. DB에는 원본 메시지도 함께 저장해 두면 나중에 다시 파싱할 수 있습니다.

## 6. 검증된 사항과 테스트

- `tests/e2e.py`: 가짜 응답으로 재생목록 생성과 기록 저장·열기·삭제, 쇼츠 생성, `#t=` 제거, 타임스탬프 링크, PDF 생성(페이지 수, 링크 주석 URL), 공유 경로, 새로고침 뒤 기록 유지를 확인합니다.
- 실제 Gemini 응답 형식은 사용자의 SKILL.md에 따라 달라집니다. 실제 응답으로 카드 분리와 PDF 레이아웃을 다시 확인해야 합니다.
- Google Cloud 설정(OAuth 동의 화면 '테스트' 상태, 테스트 사용자, 웹 클라이언트, YouTube Data API v3 사용 설정, Gemini 키 웹사이트 제한)은 사용자가 진행 중입니다. 서버로 옮기면 승인된 원본과 키 제한을 새 도메인으로 바꿔야 합니다.
